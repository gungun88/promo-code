# 积分中心与自助置顶推广 PRD

## 1. 文档信息

- 状态：需求草案，供产品与研发评审
- 目标版本：MVP
- 涉及端：公开目录、用户中心、管理后台、Node API、PostgreSQL
- 关联现状：后台已有「置顶推广」管理页和 `promo_code_placements` 展示记录；本需求将其升级为「积分中心」，支持积分兑换码和用户自助置顶，同时保留管理员人工置顶能力。

## 2. 背景与目标

目前置顶推广由管理员手动创建和维护。希望开放一个由用户自行操作的推广流程：管理员批量生成积分兑换码并通过站外渠道售卖/发放；用户在站内兑换后取得积分，再为自己发布的优惠码购买一段置顶时间。用户无需等待人工处理，管理员仍可以管理置顶结果、兑换码和异常情况。

### 2.1 目标

- 用户能查看积分余额、兑换积分、查看积分流水，并为符合条件的本人优惠码发起置顶。
- 积分仅能通过兑换码增加；置顶是积分的消费场景，不提供用户间转账、提现或积分赠送。
- 兑换码单次使用、并发安全；积分余额与流水在同一事务中更新，保证账目可追溯。
- 管理员能生成兑换码、查询兑换记录、配置兑换码购买链接，并管理人工及用户购买产生的置顶记录。
- 用户可自行完成兑换和购买流程，置顶生效不依赖管理员逐单审核。

### 2.2 非目标

- 本期不接入站内支付、自动售卡、订单支付回调或退款支付渠道。兑换码由管理员生成后通过站外发卡网售卖/发放。
- 本期不开放积分转让、提现、过期规则或邀请奖励。
- 不承诺置顶带来流量或转化，不提供广告效果数据结算。
- 不取消管理员现有人工置顶和编辑精选能力。

## 3. 角色与权限

| 角色 | 能力 |
| --- | --- |
| 未登录访客 | 浏览置顶优惠码；点击置顶入口后引导登录；不显示积分兑换入口作为可操作功能 |
| 普通登录用户 | 查看余额和个人记录、兑换未使用兑换码、为本人符合条件的优惠码购买置顶 |
| 管理员 | 生成兑换码、查看兑换码和兑换流水、配置发卡网地址、查看和管理所有置顶记录、暂停/恢复/删除置顶 |

所有权限在服务端校验。前端隐藏按钮不能作为权限控制。

## 4. 用户流程

### 4.1 兑换积分

1. 登录用户从用户中心进入「积分中心」，查看当前余额及积分记录。
2. 输入兑换码并提交。
3. 服务端校验码存在、未兑换、未撤销且未过期（若配置有效期）。
4. 在单个数据库事务中锁定兑换码、标记已兑换、增加用户余额并写入不可变积分流水。
5. 返回兑换积分数和更新后的余额；重复提交同一码应明确提示已使用，且不能重复加分。
6. 若管理员已配置发卡网地址，页面显示「获取兑换码」外链按钮；未配置或地址无效时不渲染该按钮。

### 4.2 用户购买置顶

1. 用户在自己的优惠码卡片操作区看到置顶推广入口（Pin 图标），点击打开置顶购买面板/弹窗。
2. 展示本人可置顶的已发布优惠码、剩余积分、置顶时长选项、对应积分价格和预计结束时间。
3. 用户选择优惠码和时长后确认消费；确认区再次列出消耗积分和置顶期限。
4. 服务端验证优惠码归属、发布状态、未下架、未过期，时长与价格有效、余额足够，以及赞助置顶冲突规则。
5. 在事务中扣减积分、写入负向流水并创建 sponsored placement；成功后更新余额和列表。
6. 余额不足时提供「去兑换积分」入口；无本人可置顶优惠码时引导先发布优惠码。

置顶入口仅对登录用户展示。用户不能通过修改请求为他人优惠码置顶，也不能选择任意积分数量或任意结束时间。

### 4.3 后台管理

后台侧栏将「置顶推广」改名为「积分中心」，页面以标签/子导航组织：

- **置顶记录**：现有置顶记录列表和管理操作，区分「管理员设置」和「用户积分置顶」来源。
- **生成兑换码**：生成表单、批量结果和导出/复制能力。
- **兑换码记录**：查询码批次、状态、面值、兑换用户和兑换时间。
- **积分流水**：查询兑换入账和置顶扣减记录，支持用户、流水类型、时间筛选。
- **积分设置**：维护发卡网链接和置顶时长/价格规则。

MVP 可将以上做为同一路由下的 Tabs，避免新增多个后台导航项。生成的明文兑换码仅在生成成功结果中展示一次；数据库仅存兑换码摘要，后台后续不可再次查看明文。

## 5. 页面与交互需求

### 5.1 用户中心积分中心

入口：用户中心新增「积分中心」标签/导航，路由建议 `/user/points` 或用户中心内锚点；沿用项目当前用户中心导航和登录保护方式。

页面区域：

- **积分概览**：可用积分余额；明确积分单位为整数「积分」。
- **兑换积分**：兑换码输入框、提交按钮、兑换状态提示。输入自动去除首尾空格、统一大小写；避免在错误提示或日志中回显完整兑换码。
- **获取兑换码**：仅当后台配置了合法 HTTPS URL 时显示外链按钮，`target="_blank"` 并设置 `rel="noopener noreferrer"`。链接文字为「获取兑换码」。
- **积分记录**：时间倒序分页，字段为时间、类型、变动积分、变动后余额、说明。类型至少包含「兑换入账」「置顶消费」「管理员调整（预留，仅管理员操作如纳入本期）」；只展示当前用户数据。
- **我的置顶**：展示优惠码、状态、开始/结束时间、消耗积分，可跳转对应优惠码；暂停/删除后的记录仍可追溯。

状态：首次加载、空记录、兑换处理中、兑换成功、兑换失败、网络错误。提交期间禁用重复按钮；接口幂等保证不能因重复请求重复入账。

### 5.2 优惠码卡片置顶入口

- 在现有收藏/举报操作组中加入 Pin 图标按钮，桌面和移动端均可访问。
- `title`、`aria-label` 使用明确文案「置顶推广」。已在有效用户置顶中的优惠码可显示激活状态或「管理置顶」提示。
- 未登录点击后转登录页，登录完成返回原优惠码/置顶流程。
- 用户只能对本人创建的优惠码发起置顶；非本人优惠码不展示入口。
- 入口不可替代现有收藏和举报，也不将操作图标挤出卡片可视范围。

### 5.3 置顶确认面板

- 优惠码选择器只显示当前用户可用优惠码：正常发布、未下架、未过期。
- 时长以后台配置的离散套餐呈现，例如 1、3、7 天；具体套餐和价格由上线运营配置确定，不允许用户输入自定义时长。
- 每个套餐直接显示价格，例如「7 天 · 70 积分」，并显示购买后预计结束时间。
- 显示当前余额、扣除后余额；余额不足时禁用确认并提供兑换入口。
- 若该优惠码存在时间重叠的有效赞助置顶，按确定的冲突策略阻止重复购买并显示已有结束时间。
- 提交前确认文案：「将消耗 X 积分，为该优惠码置顶 N 天。」成功后提供查看积分记录/关闭操作。

## 6. 业务规则

### 6.1 积分账户与流水

- 每个用户只有一个积分账户，余额为非负整数。
- 余额是便于读取的汇总值；每次变更必须同时创建积分流水。流水记录变动前余额、变动值、变动后余额、来源类型和来源对象。
- 兑换入账为正数，置顶消费为负数。成功提交后流水不可编辑或删除；纠错采用一笔反向补偿流水并记录管理员原因。
- 余额更新使用行锁或条件更新保证并发正确；不得先返回成功再异步补流水。
- 不允许用户直接调用接口增加余额。客户端传入的积分数、时长、价格均不得作为可信数据。

### 6.2 兑换码

- 管理员按批次生成；每批设置数量、每码积分面值、可选失效时间和内部备注。
- 码格式建议 `LS-XXXX-XXXX-XXXX`，使用密码学安全随机数生成；字符集排除容易混淆的字符。码值熵应足以抵御猜测。
- 数据库保存规范化后的 HMAC/SHA-256 摘要，不保存明文；使用兑换码专用服务端秘密时不可记录秘密。若采用带密钥 HMAC，密钥来自环境配置，不写入仓库。
- 状态：未兑换、已兑换、已撤销、已过期。撤销只允许未兑换码；已兑换码不可恢复为未兑换。
- 兑换采用事务和唯一约束/行锁。并发兑换同一码只有一个请求成功。
- 兑换码仅能兑换一次；兑换接口需限流，并对连续失败实施短期限制，避免枚举攻击。
- 批量生成必须限制单次数量上限，生成成功后只向管理员显示/下载一次，并对生成行为写审计日志。导出文件由前端生成或受保护接口一次性返回，不将原码写入普通日志。

### 6.3 积分置顶

- 积分置顶使用现有 sponsored placement 展示和排序能力，来源标识为用户积分购买；管理员人工创建的 placement 来源标识为管理员。
- 用户发起的置顶只允许关联其拥有的 promo code。归属以 `promo_codes.merchant_id` 与当前用户关联的 merchant 记录验证。
- 只允许在优惠码有效期间置顶；结束时间不能超过优惠码截止日。若优惠码无截止日期，按套餐时长计算。
- MVP 每个优惠码同一时间只允许一个有效赞助置顶；是否允许无缝续期需在实现中确定。建议将购买开始时间设为 max(当前日期, 现有有效置顶结束日)，但若允许排队续期，需同时定义已扣积分后的取消/退款策略。默认建议 MVP 禁止重叠购买，现有置顶结束后再购。
- 排序沿用现有优先级字段；积分置顶的优先级由固定系统规则决定，不允许用户自选。相同规则下按开始时间/创建时间稳定排序。
- 购买成功后立即生效。管理员暂停或删除已购买置顶时，不自动退积分；后台操作需确认并写明原因。若平台主动撤销且要补偿，管理员通过补偿流水处理并记录原因（是否纳入 MVP 需产品确认）。
- 置顶购买和扣分在一个数据库事务中完成；任何 placement 创建失败均不得扣分。

### 6.4 发卡网链接

- 后台可填写一个用于购买兑换码的 URL，允许留空。
- 非空时只接受绝对 HTTPS URL；拒绝 `javascript:`、`data:`、用户名密码内嵌、非 HTTP(S) 协议及无效 URL。
- 保存、修改操作写管理员审计日志。GET 配置接口仅返回 URL，不返回其他秘密配置。
- URL 为空时用户端不显示「获取兑换码」按钮及空占位。

## 7. 管理后台需求

### 7.1 生成兑换码

字段：

| 字段 | 规则 |
| --- | --- |
| 生成数量 | 必填正整数；MVP 建议单批 1–500，最终上限由性能评估确认 |
| 每码积分 | 必填正整数；不接受小数或 0 |
| 有效期 | 可选；留空表示永不过期 |
| 内部备注 | 可选，仅管理员可见 |

提交后展示本次生成数量、总积分面值、批次号和一次性兑换码列表；支持复制所有码/下载 CSV。明确提示关闭结果后无法再次查看明文。若下载失败，生成结果应保持当前页面状态，避免管理员误以为未生成而重复创建。

### 7.2 兑换码列表

支持批次、状态、兑换码后缀/批次号、面值、创建时间筛选；兑换码只显示掩码，不可反查完整码。列：批次、掩码、面值、状态、创建时间、失效时间、兑换用户（邮箱）、兑换时间、备注、操作。操作：撤销未兑换码；已兑换码不可撤销。

### 7.3 兑换记录与积分流水

支持按用户邮箱、流水类型、时间范围查询和分页。记录显示用户、类型、变动值、变动后余额、关联兑换批次/优惠码、时间。不得在管理表格中暴露用户密码、会话或兑换码明文。

### 7.4 置顶记录

沿用现有管理表格和暂停/恢复/删除操作，增加来源列及用户购买信息：来源（管理员/积分购买）、消耗积分、关联流水、优惠码发布者。筛选支持来源和状态。用户积分置顶的暂停、删除需要填写原因；是否进行积分补偿按明确的补偿操作处理，不能静默改余额。

### 7.5 积分设置

- 发卡网 URL（可空）。
- 置顶套餐配置：套餐天数、价格（积分），至少一个启用套餐；价格为正整数，天数为正整数，天数不超过允许上限。
- 修改套餐只影响新购买；已创建置顶记录和历史流水保存实际天数/消耗积分快照。
- 修改设置需要服务端校验并写审计日志。

## 8. 数据模型建议

实际命名遵循项目现有 snake_case。所有金额/积分字段使用整数类型。

### `user_point_accounts`

```text
user_id uuid PK FK users(id)
balance integer NOT NULL DEFAULT 0 CHECK (balance >= 0)
created_at timestamptz
updated_at timestamptz
```

### `point_code_batches`

```text
id uuid PK
created_by uuid FK admin_users(id)
quantity integer NOT NULL
points_per_code integer NOT NULL
expires_at timestamptz NULL
note text NOT NULL DEFAULT ''
created_at timestamptz NOT NULL
```

### `point_redemption_codes`

```text
id uuid PK
batch_id uuid FK point_code_batches(id)
code_hash text UNIQUE NOT NULL
code_mask text NOT NULL
points integer NOT NULL
status text CHECK (status IN ('unused', 'redeemed', 'revoked'))
expires_at timestamptz NULL
redeemed_by uuid NULL FK users(id)
redeemed_at timestamptz NULL
created_at timestamptz NOT NULL
```

过期可根据 `expires_at` 推导，无需定时任务；管理端列表可显示派生状态「已过期」。

### `point_ledger`

```text
id uuid PK
user_id uuid FK users(id)
entry_type text CHECK (entry_type IN ('redemption', 'placement_purchase', 'adjustment'))
delta integer NOT NULL CHECK (delta <> 0)
balance_after integer NOT NULL CHECK (balance_after >= 0)
redemption_code_id uuid NULL FK point_redemption_codes(id)
placement_id uuid NULL FK promo_code_placements(id)
description text NOT NULL DEFAULT ''
created_at timestamptz NOT NULL
```

对 `redemption_code_id` 建唯一索引，确保一个兑换码最多产生一笔兑换入账；置顶来源关联同一 placement 和流水。

### 现有表扩展

- `promo_code_placements` 增加 `source_type`（admin/user_points）、`points_spent`、`point_ledger_id` 或通过 ledger 反向关联。管理员旧记录默认 `admin`。
- 将套餐天数/用户确认时的计价信息持久化，以便审计；可通过 `duration_days` 保存。
- `app_settings` 保存发卡网 URL 与置顶套餐 JSON，避免本期为少量配置单独创建设置表。

## 9. API 草案

所有用户接口要求用户会话；管理接口要求管理员会话。错误响应应有稳定错误码和简短用户提示，不返回 SQL、哈希或内部秘密。

### 用户

```text
GET  /api/user/points                         # 余额和套餐设置（公开套餐，不含内部配置）
GET  /api/user/points/ledger?page=&limit=     # 当前用户积分流水
POST /api/user/points/redeem                   # { code }
POST /api/user/points/placements               # { promoCodeId, packageId }
GET  /api/user/points/placements               # 当前用户积分置顶记录
```

客户端只提交兑换码、优惠码 ID、套餐 ID。积分数、时长、用户 ID、余额均由服务端解析。

### 管理员

```text
GET  /api/admin/points/settings
PUT  /api/admin/points/settings
POST /api/admin/points/code-batches             # 创建批次并一次性返回明文码
GET  /api/admin/points/code-batches
GET  /api/admin/points/redemptions
POST /api/admin/points/codes/:id/revoke
GET  /api/admin/points/ledger
```

所有创建、撤销、设置更新、补偿操作写入 `admin_audit_logs`。列表 API 使用分页，限制最大 page size。

## 10. 安全、隐私与可靠性

- 兑换码使用密码学安全随机生成；库内仅保存摘要和掩码，兑换输入只在内存中短暂处理。
- 兑换码与登录接口应用限流；兑换失败不得区分「不存在」「已过期」「已撤销」以外的敏感内部状态（可统一提示无效或不可用）。
- 所有积分相关写操作用数据库事务；处理余额时锁定账户行，执行余额非负条件更新。
- 对客户端请求进行服务端归属、状态、价格、日期、套餐校验，防止越权和篡改费用。
- 审计日志不得包含完整兑换码、会话 token、密码或秘密配置。
- 外链使用安全 URL 校验及 `noopener noreferrer`。
- 并发兑换同码、并发扣费和重复提交均有唯一约束/幂等策略。
- 保留用户删除后的外键行为应先评估账务审计要求；建议用户账户删除时保留必要匿名化账务记录，具体沿用平台账号删除策略。

## 11. 错误与边界状态

- 兑换码为空/格式错误/不可用：提示兑换码无效或已使用，不泄露码是否存在。
- 账户余额不足：返回所需积分和当前余额；不创建 placement、不写扣分流水。
- 优惠码已下架/过期/不属于用户：拒绝操作并刷新可选列表。
- 置顶冲突：显示现有置顶结束时间，提示结束后再购买。
- 套餐已停用或价格在确认后被调整：服务端拒绝旧 package ID，要求重新选择。
- 外链配置为空：不显示购买按钮；外链无效时后台保存失败，用户端无按钮。
- 数据库事务失败：余额与流水/置顶均不应出现部分成功。

## 12. 埋点与运营指标

不采集完整兑换码。可记录：兑换提交/成功/失败类型、积分置顶确认/成功/失败原因、兑换入口点击、各置顶套餐购买数、积分发行与消耗总量。按日期聚合统计，不把敏感凭证写入事件属性。

## 13. 验收标准

### 用户兑换

- 已登录用户可兑换有效码，余额增加面值，产生一笔正向流水。
- 同一码重复提交和并发提交只能有一次成功，最终余额只增加一次。
- 已过期/已撤销/不存在/已使用码不能增加余额。
- 发卡网链接为空时不显示按钮；有效 HTTPS 链接配置后按钮正确打开新标签。
- 用户只能查询自己的余额、流水和置顶记录。

### 用户置顶

- 仅登录用户可发起；只能选择自己已发布且有效的优惠码。
- 正确套餐扣除准确积分并创建 sponsored placement，前台目录按现有规则显示置顶。
- 余额不足、无效优惠码、置顶冲突、无效套餐均不扣分。
- 并发购买不会造成负余额或多扣/少扣；任何失败不留下孤立 placement/ledger。
- 记录能显示来源、实际消耗积分和置顶期限；管理员人工置顶流程继续工作。

### 管理后台

- 管理员可按数量和面值生成批次；明文码仅在生成结果出现一次，表格只显示掩码。
- 管理员可撤销未兑换码，已兑换码不能撤销。
- 可查看兑换用户、时间、积分流水和置顶来源。
- 发卡网链接、套餐保存经过服务端校验并写审计日志。
- 后台导航显示「积分中心」，原置顶记录管理操作可在积分中心内访问。

### 工程验证

- schema 初始化/升级可在现有数据库上重复执行。
- `npm run build` 通过。
- 对数据库事务重点验证成功、余额不足、重复兑换、并发兑换/消费和置顶写入失败回滚。
- 手动检查桌面和移动端用户兑换流程及后台 Tabs/表格布局。

## 14. 发布与迁移

1. 增加积分账户、兑换码、批次和流水表；为历史 placement 设置 `source_type='admin'`，不修改历史排序和状态。
2. 部署后默认为用户余额 0，不生成虚构积分或自动迁移余额。
3. 后台先配置套餐和发卡网 URL，再开放用户入口；若未配置可用套餐，用户端隐藏/禁用置顶购买入口并显示可理解状态。
4. 分阶段启用：先管理员生成少量内部测试码验证，再开放积分入口。
5. 回滚前停止兑换和购买写操作；保留已产生账本和置顶记录，不通过删除表回滚用户资产记录。

## 15. 需产品评审定稿

1. 置顶套餐的天数与积分价格（建议先配置少量固定套餐，价格通过后台管理）。
2. 用户能否在已有置顶结束前购买续期；MVP 建议暂不允许重叠购买。
3. 管理员主动下架/暂停用户付费置顶是否需要全额或按剩余时长补偿；需有一致政策，建议由管理员显式发起补偿流水。
4. 兑换码有效期是否默认永不过期，单批数量上限和面值上限。
5. 是否在 MVP 中提供 CSV 下载、积分流水导出及管理员积分补偿功能。
